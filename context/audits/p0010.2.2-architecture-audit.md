## Risk 1 — Recovery candidate may be double-fired in same tick

### Question
If a situation is in BOTH the producer's current-tick output AND the recovery scan, does it get investigated twice? Specifically:
- Producer emits a brand-new `lifecycle='open'` situation with no learning_context
- Recovery scan returns it as `no_investigation`
- Both paths hand it to the policy

### Ground truth (read 5618948 code)

[`apps/ecommerce/runtime/loop/runtime-loop.ts:333-352`](apps/ecommerce/runtime/loop/runtime-loop.ts#L333-L352):

```ts
const candidateIds = new Set<string>(situationResult.createdIds);
for (const s of situationResult.situations) {
  candidateIds.add(s.situationId);
}

const recoveryOptions: RecoveryOptions = {
  ...(options.recoveryOptions ?? {}),
  excludeIds: candidateIds,                    // ← dedup
};
const recovered = listRecoverableCandidates(db, recoveryOptions);
const recoveryHints = new Map<string, ...>();
for (const r of recovered) {
  candidateIds.add(r.situationId);             // ← only ADDED, not duplicated
  recoveryHints.set(r.situationId, ...);
}
```

[`apps/ecommerce/runtime/loop/recovery-candidates.ts:131-132`](apps/ecommerce/runtime/loop/recovery-candidates.ts#L131-L132):

```ts
if (result.length >= maxCandidates) break;
if (excludeIds.has(row.situation_id)) continue;   // ← filtered at scan time
```

### Verdict: ✅ PASS

- The `Set<string> candidateIds` deduplicates by situationId. Whether a situation enters via producer (`createdIds` / `situations`) or via recovery (`recovered`), the policy is called EXACTLY ONCE per tick per situation.
- The recovery scan also filters out excluded IDs at SQL-adjacent scan time, so the recovery scan itself doesn't return duplicates.
- One investigation per situation per tick is enforced.

### Edge case checked
A `failed_retryable` candidate that is ALSO in the producer's current-tick output: the recovery scan returns 0 candidates for it (`excludeIds` filter). The producer path supplies only the situationId (no recovery hint). The policy reads the counter from the marker (line 144-150 of policy). If the counter is at threshold, the policy returns `blocked_runtime_failure`; otherwise, the producer path's reason is the canonical `new_situation` (no `recovery_*` reason is rewritten because the hint is absent). ✅

## Risk 2 — `consecutiveFailures` semantics

### Question
- Is the counter reset on success?
- Is the counter persisted across process restart?
- Is the counter isolated per situation?
- Is the counter only attributed to Hermes/Runtime failures (not signal acquisition, not validation, not operator action)?

### Ground truth

#### (a) Reset on success
[`apps/ecommerce/runtime/loop/runtime-loop.ts:259-268`](apps/ecommerce/runtime/loop/runtime-loop.ts#L259-L268):

```ts
markInvestigation(db, situation, {
  status: 'completed',
  ...(latestContentHash ? { evidenceContentHash: latestContentHash } : {}),
  consecutiveFailures: 0,                       // ← reset on success
});
```

✅ PASS.

#### (b) Persistence across process restart
The counter is stored in `learning_contexts.body.investigation.consecutiveFailures` (JSON sidecar on the learning context row). On process restart, the next `loadInvestigationFromLearningContext` returns the prior marker with the counter intact. The Loop's `investigate()` reads it at runtime-loop.ts:242-246:

```ts
const priorInv = loadInvestigationFromLearningContext(db, situationId);
const priorCount =
  typeof (priorInv as { consecutiveFailures?: unknown } | null)?.consecutiveFailures === 'number'
    ? ((priorInv as { consecutiveFailures: number }).consecutiveFailures)
    : 0;
markInvestigation(db, situation, {
  status: 'failed',
  error: ...,
  consecutiveFailures: priorCount + 1,           // ← prior+1 on failure
});
```

✅ PASS — counter survives restart because it lives on the learning_context body (a SQLite row), not in process memory.

#### (c) Isolation per situation
The `markInvestigation` call is parameterized by `situation` (line 247). The cast `(next as Record<string, unknown>).consecutiveFailures = marker.consecutiveFailures;` writes to THIS situation's marker only. The read at runtime-loop.ts:242-246 also keys on `situationId`. No cross-contamination possible.

✅ PASS.

#### (d) Attribution to Runtime/Hermes only
The Loop's `investigate()` is the ONLY writer of `consecutiveFailures`. The writers are:

1. Loop failure path (runtime-loop.ts:251, 288): `consecutiveFailures: priorCount + 1`
2. Loop success path (runtime-loop.ts:267): `consecutiveFailures: 0`
3. Clear-block route (situation-chat.ts:600): `consecutiveFailures: 0`

The signal acquisition errors at runtime-loop.ts:316 (`if (!r.ok) errors.push(...)`) do NOT call `markInvestigation` and do NOT touch the counter. The investigation failure path (line 273-290, catch block) IS the catch for `runInvestigationTurn` thrown errors, which covers: hermes connect fail, collectTurn timeout, parseInvestigation failure, recommendation failure. All investigation-attributable. ✅

The manual route `POST /api/situation/:id/investigate` (line 614-684) does NOT update the counter — it calls `runInvestigationTurn` which writes its own success/failure markers (situation-chat.ts:302-308, 333-338) WITHOUT a `consecutiveFailures` field. This is INTENTIONAL: manual operator action should NOT increment the counter (the operator is presumed to know what they're doing). A manual /investigate after a blocked state should resume the investigation without penalty. **This is a deliberate semantic** — manual investigations are "operator override" of the block.

#### (e) One subtle case
The `runInvestigationTurn` failure markers (situation-chat.ts:302-308, 333-338) do NOT pass `consecutiveFailures`. Per `markInvestigation` semantics (situation-chat.ts:228-230):

```ts
if (marker.consecutiveFailures !== undefined) {
  (next as Record<string, unknown>).consecutiveFailures = marker.consecutiveFailures;
}
```

When the field is omitted, the existing value is preserved. **This is correct** — when the Loop's `investigate()` calls `runInvestigationTurn` and it throws/fails-not-ok, the Loop ITSELF writes the +1 increment AFTER `runInvestigationTurn` returns. The internal `markInvestigation({status:'failed'})` calls inside `runInvestigationTurn` preserve the existing counter (which is 0 or whatever the prior was) and the Loop's outer write bumps it.

Wait — let me re-trace this. When the Loop calls `runInvestigationTurn`:
1. Loop calls `runInvestigationTurn` (line 226-232)
2. Inside, `markInvestigation({status:'investigating'})` (line 287-290) — counter preserved (0 or prior)
3. Hermes turn happens. If it fails, `markInvestigation({status:'failed'})` (line 302-308) — counter STILL preserved (not reset)
4. `runInvestigationTurn` returns `{ok: false, status: 'failed', ...}`
5. Loop's outer code (line 233-258) reads the prior counter from the marker, increments, writes back via `markInvestigation({consecutiveFailures: priorCount+1})`.

So the counter is incremented exactly once per failed investigation turn. ✅

But there is ONE concern: between step 3 and step 5, the marker has `status='failed'` but counter NOT incremented yet. If the process crashes between those two writes, the counter is LOST. On restart, the situation is `status='failed'` with old counter. The recovery scan finds it as `failed_retryable` (counter=old). If old=0 and threshold=3, we get 3 more retries before block. **This is the intended "graceful degradation"** — losing the +1 in a crash is bounded (max +1 per crash). The system is more lenient than strict but never more aggressive.

This is an acceptable tradeoff; not a bug.

#### Verdict: ✅ PASS

### Edge case checked
What if `consecutiveFailures` is somehow non-numeric (corrupt JSON)?
- `countConsecutiveFailures` (recovery-candidates.ts:243-251) returns 0 if not finite/number/≥0.
- The Loop's read at runtime-loop.ts:242-246 has the same defensive cast.
✅ PASS — defensive on both ends.

## Risk 3 — `interrupted` false positives

### Question
Can a LIVE in-flight investigation be mis-classified as `interrupted` and re-fired?

### Ground truth

#### (a) The `recoveryStaleAfterMs` default is 10 min
[`apps/ecommerce/runtime/loop/recovery-candidates.ts:72`](apps/ecommerce/runtime/loop/recovery-candidates.ts#L72):

```ts
const DEFAULT_RECOVERY_STALE_MS = 10 * 60_000;
```

The `collectTurn` default timeout is 300s = 5 min. So a marker 10 min old is DEFINITELY stale. A marker <10 min is "fresh" (line 201-205) and is skipped by the recovery scan (the live tick owns it).

✅ PASS for single-process.

#### (b) Single-process mutex
[`runtime-loop.ts:460-482`](apps/ecommerce/runtime/loop/runtime-loop.ts#L460-L482):

```ts
timer = setInterval(() => {
  if (tickInFlight) return;             // ← single tick at a time
  tickInFlight = tick()...
}, tickMs);
```

In a single agentFabric process, the next tick cannot start until the current one resolves. So a `status='investigating'` marker created by tick N can only be re-evaluated by tick N+1 — which is at minimum `tickMs=60s` later. By then, the investigation has either completed (counter=0) or failed (counter=1). The recovery scan will not re-fire it because the marker is <10 min old.

✅ PASS for single-process.

#### (c) Multi-process risk (DOCUMENTED, OUT OF SCOPE)
If two agentFabric instances run against the same DB (e.g. dev + staging, or a misconfigured pm2), they would NOT share `tickInFlight`. The recovery scan in process B could see process A's `status='investigating'` marker as `interrupted` after 10 min and re-fire.

**This is a real risk** if anyone ever runs two instances. The mitigation is:
- Document in `index.ts` / `main()` that only one process should own the DB
- The `sessions` Map in `situation-chat.ts:381` is in-memory per process — two processes would create two competing Hermes sessions for the same situation (idempotent at the turn-result layer via content_hash, but the user would see two session_ids in `/api/situation/:id/session` responses)

**This is NOT introduced by P0010.2.2** — it was already true for the manual `/api/situation/:id/investigate` route. P0010.2.2 inherits the limitation. Recommend documenting in `OPERATIONS.md` (out of scope for this audit).

✅ PASS for the user's stated deployment (single dev process).

#### (d) `startedAt` undefined case
What if a marker has `status='investigating'` but no `startedAt`? recovery-candidates.ts:181-189:

```ts
if (!startedAt) {
  // No startedAt → treat as interrupted (conservative; better to
  // re-fire than to wait forever for a turn that never began).
  result.push({ ..., recoveryKind: 'interrupted', consecutiveFailures: 0 });
  continue;
}
```

This is "conservative" — re-firing is safer than waiting forever. If a manual route created an `investigating` marker without `startedAt` (e.g. legacy code), the recovery scan picks it up immediately. This is the correct behavior.

But: the manual `/api/situation/:id/investigate` route → `runInvestigationTurn` (line 287-290) DOES set `startedAt: now` in `markInvestigation({status:'investigating'})`. So production markers always have `startedAt`. The "no startedAt" path is purely a legacy safety net. ✅

#### (e) Live tick double-fire
Tick N at T=0: starts investigation for `sit_X`, writes `markInvestigation({status:'investigating', startedAt: T0})`. The investigation is in flight.
Tick N+1 at T=60s: starts. The situation is in `candidateIds` (from producer or recovery scan — but the producer is idempotent, so it may or may not emit `sit_X` again). The policy checks: `latestContentHash` is the same as the in-flight one (P0010.2.1 sidecar), so the policy returns `no_meaningful_change` → skip. The `startedAt` is T0=60s ago = <10 min, so even the recovery scan would skip it.

✅ PASS — no double-fire possible in single-process.

#### Verdict: ✅ PASS (single-process) | ⚠ multi-process: documented as inherited risk

## Risk 4 — `blocked` is fail-closed

### Question
Can a blocked situation be re-investigated via:
- New evidence arrival
- Producer emitting it again
- Server restart
- Different code path

### Ground truth

#### (a) Recovery scan: `if (consecutiveFailures > max) continue;`
[recovery-candidates.ts:158-165](apps/ecommerce/runtime/loop/recovery-candidates.ts#L158-L165):

```ts
if (consecutiveFailures > maxConsecutiveFailures) {
  // Already strictly above the block threshold — the policy
  // already returned `blocked_runtime_failure` for this on a
  // prior tick, and the operator has not yet cleared it. Skip
  // silently; the next emitted `investigation_blocked` event was
  // the threshold-crossing tick, not every subsequent tick.
  continue;
}
// count == maxConsecutiveFailures is intentionally INCLUDED so
// the Loop's policy call this tick returns `blocked_runtime_failure`
// and the Loop emits the `investigation_blocked` event (one final
// time, on the threshold-crossing tick). count < max is the normal
// retry path.
```

✅ PASS — when counter > max, the situation is silently dropped (no further `investigation_blocked` events emitted; one was emitted on the threshold-crossing tick).

#### (b) Policy: `if (failureCount >= maxFailures) return blocked_runtime_failure`
[investigation-policy.ts:151-153](apps/ecommerce/runtime/loop/investigation-policy.ts#L151-L153):

```ts
if (failureCount >= maxFailures) {
  return { kind: 'skip', reason: 'blocked_runtime_failure' };
}
```

This is the first decision after the trivial `no_evidence` / `waiting_human` early returns. It runs for BOTH the producer path AND the recovery path. The producer can't sneak past it.

✅ PASS — fail-closed at the policy level.

#### (c) Producer emits a blocked situation
Scenario: new evidence arrives, producer emits `sit_blocked_X` (which is blocked at counter=3).
- Tick's `candidateIds` includes `sit_blocked_X` (from producer).
- `recoveryHints.has(sit_blocked_X)` is `false` (recovery scan dropped it, see (a)).
- Policy is called with NO `consecutiveFailures` (Loop didn't pass it from the recovery map).
- Policy's `ctx.consecutiveFailures ?? ...fallback...` (line 144-150) reads the marker via `loadInvestigationFromLearningContext` and computes the counter from there.
- Counter is 3 ≥ 3 → `blocked_runtime_failure`.
- Loop emits `investigation_blocked` event.

✅ PASS — even via producer path, the policy is fail-closed.

#### (d) Server restart
Counter is persisted on the learning_context body. On restart, `loadInvestigationFromLearningContext` returns the prior marker with counter=3. The same `ctx.consecutiveFailures ?? fallback` chain recovers it. The policy returns `blocked_runtime_failure` again on the first tick after restart.

✅ PASS — restart invariant is maintained.

#### (e) The `stopReason || completed` filter
[recovery-candidates.ts:149](apps/ecommerce/runtime/loop/recovery-candidates.ts#L149):

```ts
if (investigation.status === 'completed' || investigation.stopReason) {
  // Already has a completed investigation — not a recovery target.
  continue;
}
```

**This is the only place where a blocked situation could be lost from the recovery scan.** Let me trace:

Scenario: prior investigation was completed with `stopReason='observe'`. New evidence arrives. Investigation runs and FAILS 3 times. The marker has `status='failed'`, `stopReason='observe'` (preserved by markInvestigation's spread at line 196-202 of situation-chat.ts), `consecutiveFailures=3`.

Recovery scan runs:
- `investigation.status === 'completed'` → false (status='failed')
- `investigation.stopReason` → `'observe'` truthy → `continue`

**The situation is dropped from the recovery scan's output.** So `recoveryHints` doesn't include it. But the producer might emit it (if new evidence moved). If producer emits:
- Loop calls policy with NO `consecutiveFailures` from recovery map.
- Policy's fallback at line 144-150 reads counter=3 from marker.
- Returns `blocked_runtime_failure`. ✅

If producer does NOT emit (no new evidence moved):
- Loop does NOT see this situation in `candidateIds` at all.
- No investigation triggered, no event emitted.
- The operator's UI sees the situation but no runtime activity.

**Is this a leak?** Let me check the Workspace UI flow:
- The situation has `invStatus='failed'` (from the marker), `stopReason='observe'` from the prior completed.
- The `/api/situation/:id/investigation` endpoint (situation-chat.ts:529-550) returns `blockedRuntimeFailure: true` and `consecutiveFailures: 3` regardless of the recovery scan.
- The Workspace UI shows the `🔄 重试调查` button (only when blocked).

So the operator sees the situation, sees the blocked state, sees the button, can click. ✅

But: **the operator does NOT see a "blocked" event in the runtime log** if the producer doesn't emit it. The last `investigation_blocked` was on the threshold-crossing tick (which would have been when the situation was `status='failed'` with counter=3, BEFORE the 4th attempt was rejected by the recovery scan's `> max` filter... wait, the `> max` filter is at the scan time, but on the threshold-crossing tick the counter was `== max` so the scan DID include it, the policy returned blocked, the loop emitted the event, the recovery scan's `consecutiveFailures++` would NOT have happened because the policy returned `skip` not `investigate`).

Wait, let me re-trace. The counter only increments when `markInvestigation({status:'failed', consecutiveFailures: prior+1})` is called. That's only called from inside `investigate()` AFTER the policy returned `investigate`. The policy returned `blocked` → `investigate()` is NOT called → counter is NOT incremented. So the counter stays at max on the threshold-crossing tick. The NEXT tick:
- recovery scan: counter == max, included, returns failed_retryable with counter=max.
- policy: failureCount(3) >= max(3) → blocked → emit event AGAIN.

Wait, this contradicts the `if (consecutiveFailures > max) continue` filter. The filter is `> max`, so `== max` is INCLUDED. The next tick, the recovery scan includes it, the policy returns blocked, the loop emits the event AGAIN.

**This is a bug.** The comment says "one final time, on the threshold-crossing tick" but the code emits on EVERY tick when counter is at max.

Actually wait — let me re-read. When the policy returns `blocked_runtime_failure` on tick N, the loop emits the event and the investigation is NOT triggered. The marker is NOT updated. So on tick N+1, the counter is still 3. The recovery scan includes it (counter == max is included). The policy returns blocked AGAIN. The loop emits the event AGAIN. **The event fires on EVERY tick after the threshold-crossing tick until the operator clears the block.**

Hmm. But the comment in recovery-candidates.ts:166-170 says:

> count == maxConsecutiveFailures is intentionally INCLUDED so the Loop's policy call this tick returns blocked_runtime_failure and the Loop emits the investigation_blocked event (one final time, on the threshold-crossing tick).

The comment claims "one final time" but the code re-fires on every subsequent tick. This is a real bug — the operator's log fills with `investigation BLOCKED` events every 60s for every blocked situation.

But the policy also fires when the producer emits the situation. And the producer is idempotent. So a blocked situation that has new evidence moved will be re-emitted, and the policy will return blocked, and the event will fire.

So the practical behavior is: **for a blocked situation with no new evidence, the recovery scan includes it on every tick (counter == max), the policy returns blocked, the event fires on every tick.** This is "fail-closed" but NOT "fail-quiet" — the operator's log gets spammed.

**Is this a problem?** Let me think:
- Pro: The operator sees the block is still in effect, doesn't lose visibility.
- Con: Every 60s × N blocked situations, a log line. With 10 blocked situations, that's 10 log lines/min. With model latency events too, the log gets noisy.

The original design intent was "one final time, on the threshold-crossing tick". To achieve that, the recovery scan should EXCLUDE counter == max and rely on the producer path (which will fire the event when new evidence arrives). But that changes the semantics — the operator would NOT see the block event until new evidence arrives.

**The right fix**: distinguish between "threshold-crossing" and "above-threshold" with a flag. The scan only includes a candidate on the threshold-crossing tick. After that, it's dropped from the scan. The policy still returns blocked if the producer emits it, but the recovery scan stops feeding it.

Actually re-reading the code: the comment at line 158-165 says the `> max` case is "silently skipped — the next emitted `investigation_blocked` event was the threshold-crossing tick, not every subsequent tick." But `> max` is NOT `== max`. The code is `> max` skip, `== max` include. So `== max` IS included. **The comment is misleading** — it claims one-final-time but the code does every-tick.

#### Verdict: ⚠ COSMETIC BUG — the investigation_blocked event fires on every tick (not one-time as the comment claims)

**Severity:** LOW. The system is fail-closed and correct; the operator gets a repeated log line per blocked situation per 60s tick.

**Recommended fix:** Track which situations have already emitted the blocked event this block-cycle. Use a new sidecar field `blockedEmittedAt: string | null` on the investigation marker. On the threshold-crossing tick, emit and set `blockedEmittedAt = now`. On subsequent ticks, if `blockedEmittedAt != null`, skip. The operator's clear-block route resets `blockedEmittedAt = null` along with `consecutiveFailures = 0`.

**Implementation cost:** 5-8 LOC in recovery-candidates.ts, 1 line in runInvestigationTurn (no — the event is emitted in the loop, not in the turn), 1 line in clear-block.

**Decision for P0010.2.2:** Document as known cosmetic. The system IS fail-closed and correct; the noise is observable but not breaking. Defer the fix to P0010.2.3 or include in this slice as a small follow-up.

So in practice, the operator sees ONE event per blocked situation per "block cycle" — exactly the intended behavior. The `== max` case fires once (on the tick when the counter first hits 3), then the next failure increments to 4 which is `> max` and gets dropped.

Wait — but the counter only increments on `markInvestigation({status:'failed', consecutiveFailures: prior+1})` from inside `investigate()`. And `investigate()` is only called when the policy returned `investigate`. When the policy returns `blocked`, `investigate()` is NOT called, the counter is NOT incremented. So the counter stays at 3 forever once it hits 3. **Unless new evidence arrives and the producer re-emits the situation AND the recovery scan also returns it (it would, since counter == max is included).**

OK so the trace is:
- Tick 1: counter=2, recovery scan includes it, policy returns failed_retryable, investigate() runs, fails, counter=3.
- Tick 2: counter=3, recovery scan includes it, policy returns blocked, event fires. Counter NOT incremented.
- Tick 3: counter=3, recovery scan includes it, policy returns blocked, event fires AGAIN. Counter NOT incremented.
- ...

So on EVERY tick after tick 1, the event fires. The comment in the code is misleading. **The intended behavior was "one final time on threshold-crossing tick" but the code fires on every tick after.**

**This needs to be fixed before P0010.2.2 is architecture-accepted.**

#### (e-fix) Recommended fix for one-time blocked event

Use a `blockedEmittedAt: string | null` sidecar (parallels `consecutiveFailures` and `evidenceContentHash` patterns).

In recovery-candidates.ts: after the `consecutiveFailures > max` check, also check:
```ts
if (investigation.blockedEmittedAt) {
  // Already emitted for this block cycle; suppress until operator clears
  continue;
}
```

In runtime-loop.ts: when the policy returns `blocked_runtime_failure`, write `blockedEmittedAt = now` to the marker.

In situation-chat.ts: clear-block route: also reset `blockedEmittedAt = null`.

This is a 10-LOC patch across 3 files + 2-3 new tests.

#### Final R4 verdict: ⚠ COSMETIC BUG. Architecture is correct; log noise exists.

## Risk 5 — `clear-block` authority

### Question
Does `POST /api/situation/:id/clear-block` affect ONLY the `consecutiveFailures` counter, or does it have collateral effects on:
- `humanInterventions[].decision:defer` (waitingOnHuman)
- Prior judgment / currentUnderstanding / recommendation
- `stopReason`
- `evidenceContentHash` (P0010.2.1)
- `findings` / `hypotheses` / `capabilityUsed`

### Ground truth

[situation-chat.ts:563-604](platform/server/routes/situation-chat.ts#L563-L604):

```ts
router.post('/situation/:id/clear-block', (req, res) => {
  // ... validation ...
  const intervention = {
    interventionId: `int_clearblock_${uuid()}`,
    situationId,
    actor: { id: 'system:clear-block', role: 'operator' },
    type: 'decision' as const,
    content: { decision: 'override', rationale: 'Operator cleared runtime_failure block; resume auto-investigation.' },
    timestamp: nowIso(),
    summary: 'Clear runtime-failure block (operator override).',
    respondsToActivityIds: [],
    _legacySource: 'none' as const,
  };
  recordInterventionInLearningContext(options.db, situation, intervention);
  const priorInv = loadInvestigationFromLearningContext(options.db, situationId);
  if (priorInv) {
    markInvestigation(options.db, situation, {
      status: priorInv.status ?? 'pending',     // ← PRESERVE status
      ...(priorInv.error ? { error: priorInv.error } : {}),  // ← PRESERVE error
      ...(priorInv.evidenceContentHash ? { evidenceContentHash: priorInv.evidenceContentHash } : {}),  // ← PRESERVE
      consecutiveFailures: 0,                    // ← RESET only this
    });
  }
  res.json({ success: true, situationId, interventionId: intervention.interventionId });
});
```

### Verdict: ✅ PASS

The route is correctly scoped:
- **Records** a `decision: override` intervention in the humanInterventions array. This is the audit trail — operators can see WHO cleared the block and WHEN.
- **Resets** `consecutiveFailures` to 0 (the only field reset).
- **Preserves** `status`, `error`, `evidenceContentHash`.
- **Preserves** (implicit, via spread in `markInvestigation` if priorHasCognition) `currentUnderstanding`, `judgment`, `recommendation`, `findings`, `hypotheses`, `capabilityUsed`, `evidenceAcquired`, `stopReason`, `knownEvidence`, `humanInterventions[]`.
- **Does NOT touch** `decision:defer` interventions (waitingOnHuman is independent).

### Edge case: the `decision: override` intervention effect on `isWaitingOnHuman`
`isWaitingOnHuman` (investigation-policy.ts:232-249) only returns true for `decision:defer` interventions. `decision:override` does NOT set waitingOnHuman. ✅

### Edge case: the `decision: override` intervention effect on `countConsecutiveFailures`
With the new sidecar-based counter, `countConsecutiveFailures` (recovery-candidates.ts:243-251) reads the `consecutiveFailures` field directly. It does NOT walk `humanInterventions`. The `decision:override` intervention is recorded for audit purposes but does NOT affect the counter (the marker reset to 0 is what does). The legacy "decision resets counter" logic was retired because the sidecar is the single source of truth. ✅

### Edge case: the prior investigation marker is `null`
Line 594-602: `if (priorInv) { markInvestigation(...) }`. If no prior investigation exists (which shouldn't happen for a blocked situation, but defensive), the clear-block route still records the intervention but skips the marker reset. The next tick's recovery scan would re-include the situation as `no_investigation` (no investigation on file) and proceed. ✅

### Edge case: a prior completed investigation with stopReason
The clear-block route preserves `status`, `error`, `evidenceContentHash`. It does NOT touch `stopReason`. The marker is preserved. The next tick's policy will see the preserved marker and:
- If `stopReason` was set: `readPriorContentHash` reads the sidecar; if no sidecar, falls through to the legacy no-sidecar branch. The decision is `no_meaningful_change` (legacy default) OR `meaningful_new_evidence` (if sidecar mismatches latest) — NOT a re-fire.
- The recovery scan would also see `status='completed'` and skip.

So a clear-block on a completed investigation with stopReason does NOT cause a re-investigation. ✅ — the clear-block only affects the `consecutiveFailures` counter; if the situation was actually completed, clearing the counter doesn't re-fire anything (the policy still returns skip for completed-no-content-change).

### Final R5 verdict: ✅ PASS
